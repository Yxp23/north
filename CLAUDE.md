# North

North is an AI money helper for adults with cognitive disabilities, built solo for the PayPal AI Hackathon 2026. **Deadline: Thu Nov 12, 2026, 12:00 PM Pacific (3:00 PM Eastern). Submit by noon Eastern.**

**Tagline:** "You set the rules. You can override them."

**Positioning (decided Nov 7):** "AI agents can now spend your money. North is the checkpoint that makes them follow YOUR rules, built first for people with cognitive disabilities." The Money Guardian is a checkpoint ANY AI agent must pass before PayPal pays. North's own helpers (Concierge, Finder, Scam checker, Price Watcher) are the first agents; an outside assistant (any AI) connects through the **North Agent Checkpoint**, an MCP server. See "North Agent Checkpoint" below.

## What it does (the demo beats, in priority order)
1. **This week's money:** a picture-first home screen showing the weekly budget, protected rent and bills, and what's left. Every PayPal purchase is tracked automatically through webhooks. Bill reminders are in plain words.
2. **Your rules, your call:** the user writes rules in their own words ("don't let me buy big stuff late at night"). The AI turns them into structured rules, validates them and reads them back to confirm. Each wait rule gets a **strength** the user picks when making it (gentle, firm or locked: see "Guardian rule strength"). **Making a rule stricter starts right away. Weakening a rule, changing it to a weaker strength, or deleting it takes one day** (the old rule stays in force meanwhile). The user can also change or remove any rule by hand on My rules, with no AI.
3. **Scam check + Guardian block:** before paying, compare a deal's price against Channel3's 30-day price history (low/typical/high) and other sellers. A product listing with hidden prompt-injection text tricks the agent, and the Money Guardian (plain code) refuses to pay. An agent activity panel shows each step in plain words.
4. **Find it and choose it (Sat):** the Finder turns text or a photo into products ("help me choose" gives exactly 3 picks that fit this week's money). Every product screen compares all in-stock stores, cheapest first ("You pay this", "You save $X"). Photo reorder: photo of an empty item, Channel3 image search, top 3 with pictures, one tap, saved PayPal pays. A one-tap refund already exists.

5. **North Agent Checkpoint (Nov 7):** an MCP server any AI assistant can connect to with its own revocable key. It can ask to buy; the Guardian answers approve / wait / refuse with a plain reason; the person says yes on a one-tap card unless they allowed their assistant to buy must-haves under $X. An **"Ask North" box** on the home screen routes whatever the user types or uploads to the right helper.

**Cut, don't build:** separate fair-price feature, the Guardian npm package, and the "money to a person" guard. (The MCP server is no longer cut: it is the Agent Checkpoint, Nov 7.) Not in the plan now (say so if you want it back): the "Ask my supporter first" button. (Tap-to-hear and "money in real things" are back in Monday's polish.)

## The AI agents (4 real agents)
North has four agents. Each is the Claude API with tool use (the official `@anthropic-ai/sdk`), takes at most about 6 steps, and logs every step to the **activity panel** in plain words ("Reading your rule… Checking it fits your money… Done"). Models (checked against the current Claude API docs on Nov 5): **`claude-sonnet-5-5`** for the agents, **`claude-haiku-5-5`** for simple rewrites (confirmed against the live Models API, which is newer than the cached docs table). Sonnet 5.5 rejects forced `tool_choice`, so agents are steered by the prompt and everything they return is validated by code. Key: `ANTHROPIC_API_KEY`.
- **Agents never move money. Only the Guardian approves.** No agent has a checkout, charge or refund tool, and a structure test checks that agent code never imports them. **AI can only add caution:** an agent's output can make things stricter (a flag, a refuse, a new or tighter rule that the user confirms), never approve a buy or loosen a rule. Anything an agent says that becomes a number, a price or a rule is checked and rendered by code, never shown from model text.
1. **Concierge:**
   - Understands the user's message or photo and calls the other agents.
   - Turns rules written in the user's own words into structured Guardian rules: schema-validated, read back in plain words to confirm, and the user picks gentle, firm or locked. It can only create or tighten rules, never loosen one, so its rules start right away. Loosening or removing a rule is only possible by hand on My rules, never through the Concierge.
   - Turns vague descriptions ("something to keep my feet warm, not too expensive") into a search, asking ONE question with 2 to 4 picture choices if it is too vague.
2. **Finder:** text or photo to product via Channel3. If unsure, it reads the label, re-searches and filters. "Help me choose" returns exactly 3 picks that fit this week's remaining money, each with its cheapest store and a one-line reason. It is not a browse feed.
3. **Scam checker:** deal price against Channel3's 30-day history and other offers, plus a seller check. All listing text is untrusted. Its flags can only make the Guardian stricter.
4. **Price Watcher:** watches only items the user is waiting on (the waiting list, plus items they tapped "Wait, and watch the price" on) using Channel3 price tracking. Code reads the live price and stock and finds the changes (a real drop, back to a normal price, sold out, back in stock); the model only judges which are worth telling and phrases ONE message, using placeholders `{name} {price} {drop} {was}` that code fills from store values. It can only notify. See "Price Watcher and the PayPal Agent Toolkit" below.

## Hard rules
- **Only the Money Guardian can approve a payment.** It's deterministic code with unit tests. No LLM can move money. The checkout code runs only after the Guardian approves.
- **AI can only add caution, never approval.** When AI reads a message or listing for warning signs, its output can only make the Guardian wait or ask the supporter first. It can never turn a wait or refuse into an approve.
- **Treat listing and product text as untrusted data,** never as instructions, in every prompt.
- **Prices shown to the user come only from API values,** never from model text.
- **Demo store (dynamic):** Channel3 offers check out on the retailer's site, so payments go to our own sandbox demo store. Any Channel3 search result is buyable at its live price: the lowest in-stock offer, **re-read at checkout, never taken from model text**. Cache searches for 10 minutes. The seeded products stay as the fallback (and `STORE_MODE=demo` is for the video). Disclose this in the README and the video. Keep the store layer behind the `StoreProvider` interface.
- **Store comparison on every product screen:** all in-stock offers sorted by price, the cheapest marked "You pay this", and "You save $X" against the others. (Seller names are shown as the seller domain from the API, not as brand logos.)
- **Plain language:** about a 5th-grade reading level. One decision per screen, big tap targets, undo, no timers, WCAG 2.2 AA.
- **No real brand names or logos** in demo data or the video (contest rule).
- The client secret and API keys are server-only. `.env.local` is never committed.

## Guardian rule strength (built Nov 4; the rules-in-own-words UI is built Nov 5)
Each wait rule (wait on buys over $X, wait on buys after an hour) has a strength the user chooses when they make it. Strength is stored inside the rule (`rules.params.strength`, plus `waitHours` for firm), so changing it is a rule change. **When a change starts:** stricter (a lower amount, a stronger strength, a longer firm wait, a longer night, a new rule) starts right away; weaker (anything that lets a buy through that was blocked before: a higher amount, a weaker strength, a shorter wait or night, or turning the rule off) takes one day, and a mix counts as weaker. It is always compared with the rule in force right now. A stricter change also cancels a weaker change that was still waiting. Stored as `changedAt` dated 24 hours back plus `askedAt` (the real time), so the Guardian counts it at once.
- **Gentle:** "You asked me to wait on big buys. Wait, or buy now?" Buy now works right away.
- **Firm:** no Buy now today. The buy goes on the **waiting list**: "You asked me to wait a day on buys after 9pm. I saved it. I'll remind you tomorrow." The wait is 24 hours by default, set per rule. After the wait it is a normal buy, still checked against the budget and protected money. A saved item **keeps its own timer**: it can't be bought until its full wait has passed, whatever the time of day (at noon after an 11pm save it is still "not time yet"), and Buy now does not shorten it. Tapping Buy on the same product again after the wait buys it.
- **Locked:** never, while the rule is on: "You said never buy this kind of thing. To change that, edit your rule. It takes a day." No override, ever. The only ways around it: the one-day rule-change delay (the user loosens or removes the rule by hand on My rules; the old rule stays in force for 24 hours, even when the change loosens or removes the lock), or a supporter saying yes (the "Ask my supporter first" button is not in the plan now).
- **Essentials (the must-have list) pass ALL user rules**: gentle, firm, locked and a saved item's timer. A locked late-night rule must never block groceries at 11pm. They never pass the hard walls.
- **Hard walls** (refuse, no override, any strength, even after a served wait or for an essential): protected rent and bill money, going over the weekly budget, a seller flagged as a scam, any buy an AI agent started from untrusted listing text, and an unreadable price or time.
- **When rules disagree, the strictest wins:** locked, then firm, then gentle. Order of checks: walls, essentials, locked, the saved item's timer, firm, gentle.
- **AI can only add caution.** The only AI-fed Guardian inputs are the two flags (`sellerFlaggedScam`, `agentStartedFromUntrustedText`), and they can only refuse. No AI output can approve a buy or weaken a rule.
- **Every Buy now is logged** to the audit log (type `override`: what, how much, which rule), so the home screen can show "You chose Buy now 2 times this week" (`buyNowThisWeek` is already in `/api/summary`).
- **Demo user's starting rules:** wait on buys over $50 (gentle); wait on buys after 9pm (firm, 24 hours); $1,200 of rent and bills protected (a hard wall). Essentials: household, personal care, groceries, medicine.
- **Demo flow:** headphones at noon get "Wait, or buy now?" (gentle). Headphones at 11 PM are saved for later with no Buy now (firm), and stay "not time yet" even at noon. Use the Demo tools clock.
- The full decision table is `docs/guardian-decision-table.md`. It is generated from the real code, and a test fails if it drifts.

## Scam checker, tricked-agent block, activity panel (built Nov 6)
- **Scam checker** (`src/lib/agents/scam-checker/`, page `/check`, route `/api/deal-check`): the user pastes a link or ad words, or uploads a screenshot (shrunk in the browser, type checked by its first bytes). The model only reads the ad and picks the matching store listing (exact, or "similar" kind). **Code does the rest** (`src/lib/dealcheck/`): the claimed price is the lowest *item* price written in the typed words (not "save $15" or shipping), so text planted in an ad can't raise it; the seller comes from the link and is checked for copies of known sellers; offers and history come from Channel3; `computeVerdict` writes the verdict and every price. Thresholds (R = lowest real price): under 50% scam, 50-80% careful, 80-115% fine, over 115% a "price trap" (careful); a copy of a known seller is a scam; an unknown seller makes it careful (scam if the price is also too good); a made-up "was" price is careful. **An exact match is needed for "looks fine"**; similar products can only warn. A scam verdict **flags the seller** (`flagged_sellers`, never removed); checkout passes `sellerFlaggedScam` to the Guardian, which refuses.
- **Channel3 price history is empty for now** (tracking started Nov 4, `history: []`, `statistics: null`), so verdicts use today's offers and say "I don't have a price history for this yet."
- **Tricked-agent block** (key demo): the Concierge's "Ask the helper about this" reads a demo listing whose description hides instructions (`data/demo-trap-listings.json`, product `trap_earbuds`). It can only `propose_purchase`, which records data. `src/lib/proposals/judge.ts` sends every suggestion to the Guardian marked `agentStartedFromUntrustedText: true` (no way to switch it off) and the hard wall refuses it. It does not depend on the model or on the warning scan, and it has no way to charge (structure tests). Real Sonnet 5.5 resisted all 10 test injections, so the demo also has **"pretend the AI is tricked"** (demo mode only), which runs the same pipeline with a scripted fooled model, labelled as a pretend test.
- **Activity panel** is on rules, deal check, the helper, and the buy flow (`/api/checkout?stream=1`). "Show details" reveals tool calls and results (text from listings is shown as plain text).
- **Evals:** `npm run eval:scam` (32 deal cases + 10 injection listings, real API, ~1 minute). The cases are written by the developer with Claude's help, so they are a smoke test, not proof.

## Finder, live store, store comparison, Help me choose, Buy again (built Nov 7)
- **Live store** (`src/lib/store/live-store.ts`, behind `StoreProvider`): any Channel3 product is buyable at its live price = the lowest in-stock USD offer. **Checkout reads it fresh** (`getProduct(id, {fresh: true})` skips the cache), never from the browser or a model. Searches and product reads are cached 10 minutes (`channel3.ts`; history 1 hour). The 14 seeded products (12 curated + 2 made-up demo listings) are the fallback when Channel3 is down (saved price, flagged `live: false`, and the screen says so). A seeded product keeps its curated name, picture and category but uses the live price. `STORE_MODE=demo` forces demo products only (use it for the video: live results can show real brands in names, pictures and seller domains).
- **Price-changed guard:** the browser sends the price it showed (`seenCents`). It can only STOP a buy: if the fresh price differs, nothing is charged and the user sees "The price changed" (`price_changed` outcome). It never sets or approves a price.
- **Category from Channel3:** `ourCategory` (`store/map.ts`) maps the Channel3 category path to our words ("groceries", "household", "personal care", "medicine", "shoes", "clothes", "electronics", else the plain category name). A product is a must-have only if the lowest price is $50 or less, so a wrong label can never loosen the rules for a big buy. Brand names Channel3 lists for a product are stripped from its name.
- **Store comparison** (`components/store-comparison.tsx`, `store/compare.ts`) on every product screen: all in-stock offers cheapest first, "You pay this", "You save $X" vs the highest, "$Y more" on the others. A practice-shop note says our test PayPal pays.
- **Finder** (`agents/finder/finder.ts`, `/find`, `/api/find`): words or a photo. Tools `search_stores`, `search_by_picture` (only with a photo; the model can't pass its own), `filter_by_size`, `submit_result`. The model points at handles (p1, p2…); code supplies names, pictures and prices. Size is checked by code against the store's size list (many products list none: they show "I could not check the size"; confirmed sizes sort first). Product names with hidden instructions are left out and the panel warns. Agents can't import the store, so they use `src/lib/finder/` (`FindBackend`, `Shelf`, `adapter.ts` fills it from the store).
- **Help me choose** (`agents/finder/choose.ts`, `/choose`, `/api/choose`): vague words or a photo. At most ONE question with 2-4 picture choices (pictures come from store searches, never the model; `ask_question` is offered only once). Then exactly 3 picks. **Code checks the picks** (`finder/picks.ts`): real handles, no repeats, each fits the money left this week (`summarize().leftCents`, worked out in the route, never from the browser), prices from the store, and the one-line reason is used only if it has no digits, `$`, links or markup. If the model gives too few it is told to fix them; fewer than 3 fit means fewer are shown; none fit gives a kind "nothing fits this week" with the lowest price seen. Picks only open the product; buying is still a separate tap through the Guardian.
- **Buy this again** (`/reorder`): photo of an empty item (needs a photo) -> `/api/find` with `mode: "reorder"` -> top 3 with pictures -> one tap on "Buy this one" -> the same guarded checkout (all rules apply, wait/saved/refused screens too) -> picture receipt with "You'll still have $X this week." (`leftCents` on the `paid` outcome).
- `loop.ts` accepts `finalTools` (more than one tool can end a run: ask a question or give the picks).
- **Not built:** category rules ("no more shoes"). It needs a new Guardian rule type, timing/strength rules, a Supabase migration (rules table), the Concierge's output schema, and the rules screens.

## Price Watcher and the PayPal Agent Toolkit (built Nov 7)
- **PayPal Agent Toolkit** (`@paypal/agent-toolkit` 1.11.0, checked against its README and package on Nov 7). Used **read-only**: `src/lib/paypal-toolkit/reader.ts` is the only file that imports it, builds it with only `orders.get` and `transactions.list` turned on, and `callToolkit` refuses every other method (`get_order` and `list_transactions` only). Its `create_order` has no saved-account (vault) option, and `pay_order`, refunds and invoices would move money outside the Guardian, so **checkout stays our own guarded code** (`structure.test.ts` in `payments-help/` checks all of this). It is called directly through the `openai` entry's `handleToolCall`, with no OpenAI client. `get_order` works in the sandbox. **`list_transactions` returns 403 until Transaction Search is turned on for the sandbox app** in the PayPal developer dashboard; the app says so plainly.
- **Payments helper** (`/payments`, `agents/payments/payments.ts`, `/api/concierge/payments`): "Did my last order go through?" / "Show my last payments" / own words. Tools `my_recent_orders`, `order_status` (toolkit `get_order`), `account_activity` (toolkit `list_transactions`), `submit_answer`. The model points at handles (o1…); code owns the PayPal order ids. Every amount and status comes from North's record or PayPal's answer, and a mismatch is shown ("PayPal says Refunded. North says Paid."). The model's sentence is used only if it has no digits, `$`, links or number words (`plainLine(..., {noNumberWords: true})`). The activity panel names each "PayPal (Agent Toolkit)" call.
- **Price Watcher** (`agents/watcher/watcher.ts`, orchestrator `src/lib/watcher/run.ts`, state `watcher/state.ts`, facts and words `watcher/facts.ts`). Watch set = waiting-list items (synced automatically) plus items the user chose to wait on (`/api/watch` start). On the first check it asks Channel3 to start price tracking. A change is a candidate only if code finds it: drop of at least 3% and $1 below the price when the user started waiting; sold out; back in stock; back to a normal price (needs Channel3 history). The same news is never told twice (`lastNoticeKey`). The model can only choose among code's candidates and write the message; a message with its own number, price, link or number word falls back to code's words. If the AI fails, nothing is marked as seen, so the news is not lost. It writes only watches, notices and an audit entry: never purchases (`watcher/structure.test.ts`). A notice's "Look at it" opens the product; a buy still goes through the Guardian. Price news shows on the home screen.
- **Run it:** "Check prices now" and "Check prices now (pretend they dropped 20%)" in Demo tools (pretend is demo mode only, labelled, and never remembered as the real price). The schedule is `GET /api/watch/run` with `Authorization: Bearer $CRON_SECRET`: add the cron entry in `vercel.json` at deploy time (Tuesday).
- **Storage:** watches and notices live in one JSON column, `users.price_watch` (migration `20261107000000_north_price_watcher.sql`, which also replaces `ledger_apply` and `ledger_reset`). Until it is run, the Supabase-backed app throws "database is out of date".

## North Agent Checkpoint (decided Nov 7)
**What it is:** the Guardian as a checkpoint for outside AI agents. An MCP server (official TypeScript SDK, `@modelcontextprotocol/server` / `/client` v2, checked against the current docs on Nov 7) served over Streamable HTTP at `/api/mcp` (`createMcpHandler`, web-standard, one fresh server per request). The agent holds only the MCP URL and its North key. It never receives PayPal tokens, the vault, account details, or the protected-money amount.
- **Tools:** `request_purchase(product or Channel3 id, quantity 1-5, reason, triggered_by)`, `get_spending_rules` (plain words only), `get_week_money` (left / plan / spent only), plus a read-only `get_request_status(request_id)` so an agent can follow up on a request that needed a person. There is no tool that pays, refunds, or changes a rule.
- **Every request goes through the existing Guardian** (`decide`), with the price re-read from the store (never from the agent), `overrideWait: false` always, and the untrusted flag (`agentStartedFromUntrustedText`) set when the agent's `reason` or the listing's own text holds hidden instructions, or the agent says it was triggered by web content. The answer back is `approve | wait | refuse` plus the Guardian's plain reason, so a well-behaved agent can explain it to the person.
- **Agent permissions are a user rule:** default **"Ask me every time"**; optional **"My assistant can buy must-have things under $X without asking."** It is stored with the same timing as other rules (`StoredChangeable`): letting the assistant do MORE (turning it on, a higher $X) takes one day; less (off, a lower $X) starts at once. By hand on My rules. The Concierge may only tighten rules, so it can never turn auto-buy on.
- **When the person must say yes:** an approved request that needs asking shows a one-tap card on the home screen ("Your assistant wants to buy Warm Socks, $11. Yes / No"). A gentle-wait result also needs the person, and **only the person's Yes can be a "Buy now" override**; an agent can never use it. A firm wait saves to the waiting list as usual. Hard walls (rent and bills, budget, scam seller, untrusted text) refuse with no override for anyone. Auto-buy happens only when ALL hold: the product was named by id (not a search), it is a must-have, the total is under $X (rule in force), and the Guardian says approve.
- **Connected assistants:** each gets its own key (shown once, only its hash is stored), revocable at once with Disconnect on My rules. Every request goes in the audit log ("An assistant asked to buy…") and the activity panel (steps are stored on each request). Requests are rate-limited per assistant.
- **Payment happens only inside North** via the saved PayPal, after the Guardian (and the person, if required). The agent code can't reach checkout, PayPal or the ledger (structure tests).
- **Try it as an outside agent:** `node scripts/mcp-smoke.mjs` (a plain script that connects to a running app over real HTTP MCP with its own key, asks to buy, gets WAIT / REFUSE, is turned away after Disconnect).
- **Storage:** connected assistants, requests and the permission live in one JSON column, `users.agent_checkpoint` (migration `20261108000000_north_agent_checkpoint.sql`, which also replaces `ledger_apply` and `ledger_reset`; Start over disconnects every assistant). Until it is run, the Supabase-backed app throws "database is out of date".
- **Checkout now takes a quantity** (1-5, the Guardian and PayPal see the total); the web UI never sends one, only the checkpoint does.
- **Demo client:** `/assistant-demo` (demo mode): a generic "Any AI assistant" chat (Claude via the API) that connects to North only through the MCP server, so the video can show an outside agent being stopped. No third-party product UI or logos. Real Sonnet resisted every injection so far, so it also has the labelled **"pretend this assistant is tricked by a listing"** button (a scripted fooled model).
- **Known gap (tell judges honestly):** the web UI routes (`/api/checkout`, `/api/agents`…) have no user login yet (single demo user). An agent key is accepted ONLY on `/api/mcp`, but a production version needs a real user session (Supabase Auth) in front of every UI route so an agent can't call them directly. Deploy-week item.

## Ask North (decided Nov 7)
A box on the home screen. The Concierge reads whatever the user types or uploads and **routes** it to the right helper or tool: Scam checker, Finder, Help me choose, a new rule (opens the rule helper; nothing is saved until the person confirms), or the Payments helper. The handoff shows in the activity panel ("Asking the Scam checker…"). The existing pages stay as shortcuts. **Routing can't move money:** the router has one tool that names a destination, and the destinations are the existing read-only/notify-only helpers.

## Security hardening (built Nov 8) - see docs/security.md and docs/threat-model.md
Login on every web route (Supabase Auth password check, own signed session cookie, CSRF token + Origin check, real logout), proxy + security headers + CSP. Every PayPal charge/refund needs a SIGNED single-use 2-minute Guardian approval bound to user, product, cents, currency, quantity (`guardian/signed.ts`, `authorize.ts`); the database also re-checks budget and protected money in `ledger_apply`. Tamper-evident audit log (`npm run audit:verify`). Persistent rate limits, idempotency (`request_key`, tap ids, webhook ids), assistant scopes, demo tools off in production unless `DEMO_MODE=1` and `DEMO_DEPLOYMENT=1` (practice account only). The Guardian fails closed on any odd setting, and has property tests (fast-check). `attacker/` is a permanent AI red team (`npm run attack -- --rounds N`) with an independent judge; attacks that matter live in `attacker/corpus` and are replayed by `npm test`. A "Try to break North" page (`/try-to-break`, demo only). Newest migration: `20261109000000_north_security_hardening.sql` (must be run; the app refuses to run without it). New env: `NORTH_SECRET`, `SUPABASE_PUBLISHABLE_KEY`, `NORTH_SITE_URL`, `DEMO_DEPLOYMENT`, `DEMO_USER_ID`, `PAYMENTS_MODE=simulated` (dev/tests/attacker only).

## Verified API details (checked against current docs; don't go from memory)

### PayPal (sandbox: https://api-m.sandbox.paypal.com)
- **Auth:** `POST /v1/oauth2/token`, Basic auth with client ID and secret, body `grant_type=client_credentials`.
- **JS SDK v6, not v5:**
  - Script: `https://www.sandbox.paypal.com/web-sdk/v6/core`
  - `window.paypal.createInstance({ clientId, components: ["paypal-payments"], pageType: "checkout" })`
  - `sdk.createPayPalOneTimePaymentSession({ onApprove, onCancel, onError })`. `onApprove` receives `{ orderId }`.
  - In the click handler: `session.start({ presentationMode: "auto" }, createOrderPromise)`. **No `await` before `session.start`**, or the popup gets blocked. `createOrderPromise` resolves to `{ orderId }`.
- **Saving PayPal (no purchase, no charge): vault-only with setup tokens.** Verified in sandbox on Nov 4 up to the PayPal login popup:
  - Server: `POST /v1/oauth2/token` with `grant_type=client_credentials&response_type=client_token&intent=sdk_init` gives a browser-safe client token.
  - Browser: `createInstance({ clientToken, components: ["paypal-payments"], pageType: "checkout" })`, then `sdk.findEligibleMethods({ currencyCode: "USD", paymentFlow: "VAULT_WITHOUT_PAYMENT" })`, then `sdk.createPayPalSavePaymentSession({ onApprove, onCancel, onError })`.
  - Click handler (no `await` before it): `session.start({ presentationMode: "auto" }, promise)`, where the promise resolves to `{ setupToken: id }`. `onApprove` receives `data.vaultSetupToken`.
  - Server: `POST /v3/vault/setup-tokens` with `payment_source.paypal { usage_type: "MERCHANT", customer_type: "CONSUMER", experience_context { return_url, cancel_url, vault_instruction: "ON_PAYER_APPROVAL" } }` returns `PAYER_ACTION_REQUIRED` and an `id`.
  - After approval: `POST /v3/vault/payment-tokens` with `{ payment_source: { token: { id: <setup token>, type: "SETUP_TOKEN" } } }`. The response `id` is the permanent vault token. Keep it server-side; never send it to the browser or log it.
  - The old way (a $5 purchase with `store_in_vault`) is gone: it moved money outside the Guardian.
- **Later purchase, no popup:** `POST /v2/checkout/orders` with `payment_source: { paypal: { vault_id } }`. **Confirmed in sandbox on Nov 4:** the order comes back `COMPLETED` immediately, with no popup and no separate capture. Still handle `APPROVED` or `CREATED` (capture it) as a safety net, and log the raw response.
- **Refund:** `POST /v2/payments/captures/{captureId}/refund`. **Confirmed in sandbox on Nov 4.** A second refund on the same capture returns `CAPTURE_FULLY_REFUNDED`; the app must treat that as success and show "Already refunded", not an error.
- Send a `PayPal-Request-Id` (UUID) on every POST, so retries never charge twice.
- **Sandbox app setup:** check Accept payments, then turn on Vault under Advanced options. Log in to the popup with the personal sandbox account.
- **Fallback if saved-account charges fail:** one-tap approval per purchase.
- **Webhooks in the sandbox are only partly reliable.** In testing, PayPal sometimes never created an event (its own event log had no entry), so about half of the events arrived. Never depend on a webhook alone: record the payment from the capture response and the refund from the refund response, and use webhooks only to confirm. Every event that did arrive verified fine.
- **Webhooks can't reach localhost.** For local testing, use a tunnel (`npx cloudflared tunnel --url http://localhost:3000`) or deploy to Vercel early, then register `/api/paypal/webhook` in the sandbox app for `PAYMENT.CAPTURE.COMPLETED` and `PAYMENT.CAPTURE.REFUNDED`. Verify signatures with `POST /v1/notifications/verify-webhook-signature`. Until then, record payments from the capture response.
- PayPal requires risk data (FraudNet) for token payments in production. It isn't needed in sandbox; mention it in the README as production work.

### Channel3 (REST; don't use `@channel3/sdk`, since v4.6 renamed its methods and doesn't match the docs)
- **Base:** `https://api.trychannel3.com`; **header:** `x-api-key`.
- **Search:** `POST /v1/search` with `{ query?, base64_image?, limit }`. `base64_image` is raw base64 with the `data:` prefix stripped. The response is `products[]`, each with `id`, `title`, `brands[]`, `images[]` (`url`, `is_main_image`) and `offers[]` (`domain`, `price.price`, `price.currency`, `price.compare_at_price`, `availability`).
- **Product:** `GET /v1/products/{id}`.
- **Start tracking:** `POST /v0/price-tracking/start` with `{ canonical_product_id }`. History only builds from the day tracking starts.
- **History:** `GET /v0/price-tracking/history/{id}?days=30`, returning `history[]` and `statistics { current_price, min_price, max_price, mean, current_status: "low" | "typical" | "high" }`.
- Cache every response.
